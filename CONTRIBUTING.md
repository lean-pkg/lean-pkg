# Contributing to lean-pkg

Thank you for helping. This repository holds the `lean-pkg` tool and its
public [index](docs/index-catalog.md). The rules below follow Mathlib's
contribution norms, including its rules on AI assistance. Who decides what is
in [GOVERNANCE.md](GOVERNANCE.md); a soundness or security problem goes
privately, by [SECURITY.md](SECURITY.md), not into an issue.

## AI assistance rules

1. **Disclosure is mandatory.** If an AI system helped write code, tests,
   documentation or a Lean proof in your pull request, say so in the PR
   description. Name the model or tool and the parts it touched. "No AI
   assistance" is also a valid statement, and we ask for it explicitly.
2. **Use your own words in review threads.** Write review comments and
   replies yourself. Do not paste generated text into a discussion as if it
   were your own reasoning.
3. **You must understand what you submit.** You are responsible for every
   line. Be ready to explain any change and to defend it under review without
   re-asking a model.
4. **New contributors: one open pull request at a time.** Wait until your
   first PR is merged or closed before opening the next one.

## Development setup

Python 3.11 or later. From a clone:

```bash
python3 -m pip install -e '.[test]'      # or: uv pip install -e '.[test]'
git config core.hooksPath .githooks      # optional: the pre-push hook runs `make check`
make check                               # the gate every pull request must pass
```

The `make` targets:

| Target | What it runs |
|---|---|
| `make check` | `test`, `boundary`, `tabs`, `versions`, `changelog`, `reuse`: the release gate, and what hosted CI runs |
| `make test` | the full pytest suite (works without installing: `pythonpath = src`) |
| `make boundary` | `scripts/private-boundary-check.sh`: no private host, user or path in what git would ship |
| `make tabs` | no tab characters in source or documentation (use spaces) |
| `make versions` | `pyproject.toml`, `CITATION.cff`, `CHANGELOG.md` and the package agree on the version |
| `make changelog` | each released `## [X.Y.Z]` section of `CHANGELOG.md` reads as it did at tag `vX.Y.Z` (only record-doi's DOI line may be added); new entries go under `## [Unreleased]`, under the heading RELEASING.md "CHANGELOG headings" assigns, agreeing with the upgrade record |
| `make reuse` | REUSE compliance (skipped, not passed, without `pipx install reuse`) |
| `make goldens` | re-record the golden CLI contract after an intended help or JSON change |
| `make docs` | rewrite the generated files (`llms.txt`, `docs/llms.txt`, `index/README.md`, the command reference, `src/lean_pkg/data/upgrade-breaking.yaml`) |
| `make history` | the boundary scan over every blob and commit message reachable from any ref |
| `make public-safety` | lean-pkg's own public-safety scan, history included (needs the untracked `.lean-pkg-private-patterns`; maintainers only) |

`make release`, `make cut-release` and `make record-doi` are the
maintainer's release steps ([RELEASING.md](RELEASING.md)).

## What a change must carry

- **Tests.** Every new behaviour and every refusal path gets a test. A fix
  comes with a test that fails on the base revision; say how it failed in
  the PR. Tests use temporary registries (`--registry` under a temporary
  directory), never a real one.
- **The golden CLI contract.** `tests/test_cli_contract_*.py` pin the command-line
  interface: the `--help` text of every command (`tests/golden/help/`), the
  top-level keys of each `--json` payload (`tests/golden/json-keys.json`), an
  argv table of which invocations write and lock the registry, and a corpus
  of quoted invocations that must keep parsing (`tests/data/compat-corpus.txt`,
  regenerated by `scripts/extract-compat-corpus.py`, scrubbed to flags,
  command names and the placeholder `demo`). When a change to help text or a
  JSON payload is intended, run `make goldens` and review `git diff tests/golden`.
  Adding a key is fine; removing or renaming a key, command or flag needs a
  [proposal](docs/proposals/README.md).
- **Generated files.** Run `make docs` when `LLMS_TEXT`, an index entry or
  a breaking upgrade-record entry changes (RELEASING.md, "The
  breaking-entries file"); CI fails on a stale generated file.
- **Public safety.** No host names, user names, local paths, student data or
  private paper names, in files, commit messages or PR text: GitHub keeps
  them after a force-push. `make boundary` checks the tree and CI checks the
  history; use placeholders such as `demo` and `~/work/demo`.
- **Docs.** A user-visible change updates its documented home: README.md,
  docs/index.md or docs/how-to.md for a new command, its notes and an
  example in docs/_commands/ (then `make docs` regenerates its page in
  docs/commands/), and the agent contract (`lean-pkg llms`).

## CHANGELOG entries

Every user-visible change adds an entry under `## [Unreleased]` in
[CHANGELOG.md](CHANGELOG.md), in the section that matches it: `### Added` (a
new command, flag, field or feature), `### Changed` (behaviour or a format;
a format change names its migration; release tooling, tests or CI),
`### Fixed`, or `### Documentation` (documentation only). A pull request the
upgrade record lists under `no_author_change` never goes under `### Added`:
`make changelog` refuses it (RELEASING.md, "CHANGELOG headings"). Write what a user can now
do or what was wrong, the command names, and the doc that explains it. Never
edit a released section; the maintainer moves Unreleased into a version at
release time, and the sections decide the version number (RELEASING.md,
"When to tag"). Refactors and docs polish need no entry.

## Toolchain advisories

[`src/lean_pkg/data/toolchain-advisories.yaml`](src/lean_pkg/data/toolchain-advisories.yaml)
lists Lean releases with a known kernel or runtime soundness bug; `gate`,
`receipt check`, `palomar check` and the page warn on them
([receipts](docs/receipts.md#checking-a-published-packages-receipts-receipt-check)).
To add an entry, when a Lean point release fixes such a bug:

1. **Primary sources only.** The Lean release notes
   (`https://lean-lang.org/doc/reference/latest/releases/vX.Y.Z/`) and the
   lean4 issue and pull request they cite (labels `soundness`,
   `runtime-soundness`). A forum post, a third party's changelog or a
   summary is a pointer, not a source: confirm it upstream or leave the entry
   out. List the release notes first; the WARN line links the first link.
2. **One entry per fixed release**, `id` `lean-vX.Y.Z-<topic>`, `fixed_in`
   the first stable release with the fix, `summary` one factual paragraph in
   the release notes' own terms (what it lets through, and whether
   comparator or an independent kernel catches it), `date_added` today.
3. **Which releases lack the fix.** `affected.below` is normally `fixed_in`.
   Then list in `affected.also` every rc of a later line cut before the fix
   was backported to it: for each tag `vA.B.C-rcN` at or above `below`, check
   whether the fix PR's merge commit is an ancestor of the tag (`git merge-base --is-ancestor SHA TAG`) or a backport commit naming the PR is in
   the tag's history since its fork from master. `affected.nightlies_through`
   is the day the last fix of the entry merged into master.
4. **Gates.** `python3 -m pytest -q tests/test_toolchain_advisories.py`: the
   file is validated strictly when loaded (closed keys; a malformed file
   fails the tests, never a user's command), and the version table in that
   test gets the new entry's rows. Add a CHANGELOG `### Changed` line (the
   warning now names more toolchains). No page goes stale because of it:
   `page --check` leaves advisory lines out of its comparison and prints a
   NOTE, and the next `page --write` shows the line, so authors need not act.

Never remove an entry because a newer release exists: receipts made on the
affected toolchain stay affected. Correct an entry only when upstream
corrects its notes, and say so in the CHANGELOG.

## Reporting a bug

Run `lean-pkg report --command "ARGS"` (add `--package NAME` when it
concerns one package; `--body TEXT` or `--from-log FILE` when there is no
command to re-run). It drafts an issue in the shape of the bug template,
with the version, `doctor` and `comparator host-check` lines, and every
private path and address redacted; `--yes` files it. A good bug report has:

- the version line of `lean-pkg --version` and your Python version;
- which track you are on: a paper (formalizing a paper's results) or a
  Lean package (a library, a Mathlib contribution or a public GitHub
  repository with no manuscript); the bug template asks;
- the exact command, run with `--json`, and its full output, including the
  JSON reason;
- what you expected instead;
- the smallest registry, receipt or package that reproduces it, with private
  paths replaced by placeholders.

A report that the tool accepted evidence it should have refused (a false
"verified") is a security report: see [SECURITY.md](SECURITY.md).

## From a field report to a pull request

A field report is what a package author saw while using lean-pkg on a real
package: several findings from one session, each with a severity, and
which track (paper or Lean package) the session was on. File it with the
*Field report* issue template. The maintainer (or the operations
agent, see [GOVERNANCE.md](GOVERNANCE.md)) triages it: each finding is
reproduced on `main`, split into one pull request per logical change, and the
PR scope names the report (for example "field report #5, finding 2"). A
finding that changes a format, removes a command or changes what a receipt
proves goes through a [design proposal](docs/proposals/README.md) first.
Findings that are not taken are answered in the issue with the reason.

## Pull requests

Contributions are pull requests against `main`, squash-merged by a
maintainer once CI is green and review is done.

- **One logical change per PR.** Title and squash subject:
  `area: what changed`, in the imperative or as a noun phrase, with the issue number when
  there is one, for example `receipt: --compress-log seals the log (#132)`.
- **Evidence, not only ticked boxes.** The pull request template asks for the
  commands that actually ran with their observed results (a gate that could
  not run is listed as not run, with the reason), how a fix's new test fails
  on the base revision, the trust-boundary effect, and the remaining proof
  gaps. Anything not established is written "unknown", never "none" or "no".
- **Index entries**: a PR adds `index/<name>/` (an `entry.yaml` of schema
  `index-entry/2` and the verbatim receipt copies under `receipts/`) written
  by `lean-pkg index add`, plus the re-rendered `index/README.md`. Code and
  logs stay in the package repository, not here. Before merging, the
  maintainer runs `lean-pkg index check --clone <name>`, which clones the
  package at the pin, re-derives the receipts and logs from bytes, checks the
  toolchain, `lake-manifest.json`, license and tag at the pin, and recomputes
  the trust level; its output goes into the review. A PR cannot merge without
  a passing run. See [The index](docs/index-catalog.md).
- **Human review** covers what machines cannot check: whether the Lean
  statement says what the paper says, naming, and documentation. Reviewers
  do not have to be maintainers.
- **Format and command changes** (an on-disk schema, a removed or renamed
  command, flag or JSON key, what a receipt or gate trusts) start as a
  [design proposal](docs/proposals/README.md), not as a PR.

## Code of conduct

We follow the norms of the Lean community. Be kind, be precise, assume good
faith. The maintainer may hide comments or lock threads that break this.
