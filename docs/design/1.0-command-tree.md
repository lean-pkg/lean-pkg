# Proposal: the 1.0 command tree and format freeze

Status: **proposal, not accepted**. Date: 2026-10-17. Nothing in this
document changes a command. Removing or renaming a command is the
maintainer's decision; this page lays out the options, the evidence and a
recommendation, so that the decision can be made once and recorded in
`docs/decisions/`.

Scope: roadmap wave 2, "Simplify to 1.0". It covers the command and flag
inventory, real usage, a proposed 1.0 tree with a migration and deprecation
policy, and the on-disk format inventory against the 1.0.0 criteria in
[RELEASING.md](../../RELEASING.md#100). It does not design `lean-pkg new`
(wave 1) or CI-runner receipts (wave 3); where the tree depends on them it
says so.

## Summary

- lean-pkg 0.9.0 has **34 top-level commands**, **52 parser nodes** (with
  subcommands), three pseudo-subcommands hidden behind a positional
  (`comparator config`, `comparator host-check`, `formalization anchor`),
  three more executables
  (`comparator-receipt`, `lean-exercise`, `lean-pkg-extract`), and **287
  command-specific options** (172 distinct names) on top of 8 global ones.
- Real use is concentrated: in the last 30 days, `update`, `gate`, `claim`,
  `release`, `claims sync` and `register` produce 90% of the registry's
  write events, and `comparator-receipt`, `update`, `gate`, `status` and
  `page` lead the shell invocations. About a third of the surface
  (`reservoir check`, `claims migrate`, `receipt local`, `publish`,
  `leases`, `renew` as typed commands, `index migrate`) is used rarely or
  never outside the test suite.
- The newcomer path today needs most of the 34 commands because three
  different jobs share names: `release` both releases a lease and exports a
  repository; `comparator` both attaches a receipt and (through a positional
  keyword) writes configurations and checks the host; `publish` is a
  read-only checklist while `promote --yes` publishes.
- Proposal: five newcomer verbs (`new`, `verify`, `status`, `page`,
  `publish`), shared by two product tracks (a **paper** whose companion is
  the Lean code, or a **Lean package** that is itself the product: a public
  repository or a Mathlib contribution), an author surface of package verbs plus evidence nouns, and a
  coordination surface (`lease`, `registry`, `repo`) for multi-agent
  registries. Every current spelling stays as a **permanent alias** (an
  ARGV_TABLE row), so no script breaks; 11 top-level names leave the
  first page of help.
- Formats: seven of the on-disk formats carry a version and have a migration
  or a compatible reader. Two do not: the **lower-tier receipt** has no
  schema key, and the **event log** has none. Those two, a formats page, and
  a compatibility corpus in the tests are what is missing for "versioned
  formats with migrations".

### Flags

- 287 command-specific options. The heaviest commands: `update` 39,
  `comparator` 30 (six modes on one usage line), `receipt slurm` and
  `receipt systemd` 24 each, `index add` and `formalization` 20, `register`
  19, `claims rebase` 17, `search` 16, `release` 16.
- `--repo` has three meanings: a remote URL (`register`, `update`,
  `index add`), a checkout directory (`gate`, `comparator`, `page`, `next`,
  `palomar check`, `receipt`), and a GitHub repository slug (`report`).
  `--repo-dir` (`index add`, `index check`, `search`) and `--checkout`
  (`comparator config`) are two more spellings of "a checkout directory".
- Five spellings of "really do it": `--yes` (`promote`, `report`),
  `--write` (`page`, `formalization`, `claims mark`, `palomar port-modules`,
  `comparator config --migrate-signoff`), `--fix` (`audit`), `--force`
  (five commands, three meanings), and writing by default with `--dry-run`
  to opt out (`register`, `migrate`, `claims migrate`, `palomar prepare`,
  and `update`/`release` only for some modes), while `claims mark`,
  `palomar port-modules` and `report` accept a `--dry-run` that is already
  their default. `publish` accepts only `--dry-run`.
- `receipt slurm --commit SHA` and `receipt systemd --commit SHA` name the
  receipt's commit, while the global `--commit` means "commit the registry
  files"; the same spelling has two meanings on one command line.
- `--agent` appears on 18 commands, sometimes required for a write and
  sometimes only "with `--write`".
- `--fields` exists on `status`, `list` and `board` only; there is no
  `--jq`.
- Help text is dense: `docs/cli.md` is 19,000 words and its longest table
  row (`gate`) is 10,500 characters.

### What the evidence says

1. The lease commands are heavily used, but only by agents sharing one
   registry. A newcomer with one package never needs them.
2. `update` is the workhorse (199 events): it is the de facto "edit the
   record" verb, and its 39 options are where field reports have landed.
3. `comparator-receipt` is the most-run program and is not a `lean-pkg`
   subcommand, so the main tool's help never shows the step people run most.
4. `publish` (the read-only checklist) is almost unused; `promote` is what
   people run. The newcomer-facing name is the unused one.
5. Readiness checks (`reservoir check`, `palomar check`, `public-safety`,
   `coverage check`, `claims check`) are run by humans rarely; they matter
   as steps inside `gate --check`, `page --check` and `promote`.

## 4. Proposed 1.0 command tree

### Principles

1. **The package is the implied noun.** A top-level verb acts on one
   package (`lean-pkg status NAME`), as in cargo or npm. Every other object
   gets a noun with verbs (`lean-pkg lease claim NAME`,
   `lean-pkg receipt slurm`). This is how the 1.0 criterion "commands are
   grouped as noun-verb pairs" is met without writing
   `lean-pkg package status`.
2. **A noun alone is read-only.** `lean-pkg claims NAME` lists,
   `lean-pkg comparator NAME` checks; anything that writes has an explicit
   verb.
3. **One name, one job.** No command changes jobs with a flag
   (`release --fresh-repo`) or a positional keyword (`comparator config`).
4. **Old spellings never break.** Each current spelling becomes a
   permanent alias, pinned by an ARGV_TABLE row; aliases are left out of the
   first page of `--help` and listed by `lean-pkg help aliases`.
5. **Help in tiers.** `lean-pkg --help` shows the five newcomer verbs and
   one line pointing at `lean-pkg help all`; the full tree is grouped as
   below.

### Tier 1: newcomer (five verbs)

| 1.0 command | Today | What it does |
|---|---|---|

A wrapper only: it writes the same receipts and events as the three steps run by hand. The CI-runner route (wave 3) plugs in here |

Helpers always visible: `doctor`, `help`.

### Two product tracks on the newcomer page

There are two kinds of final product, and the newcomer page shows a path
for each. Both share the five verbs; they differ in what `page` maps (the
`kind` of `coverage.yaml`, `paper` or `library`, already in coverage/1
since 0.9.0) and in what follows `publish`.

| Step | Track P: the paper is the product | Track L: the Lean package is the product |
|---|---|---|
| Start | `new DIR` (kind `paper`) | `new DIR --kind library`, or `new --adopt DIR` for an existing repository |
| Bind the source | `formalization anchor NAME --arxiv IDvN`; `claims rebase` for a new version | none: the rows are the library's main results |
| Verify | `verify NAME` | `verify NAME` |
| Page | `page NAME --write`: the paper-Lean map, *Not formalized* | `page NAME --write`: *Main results*, no manuscript |
| Publish | `publish NAME --yes` (public repository, cited from the paper) | `publish NAME --yes` (public repository) |
| After | `palomar prepare` and `record palomar-*`; `record doi-minted` | public repository: `index add`, `reservoir check`, `record reservoir-listed`, `record doi-minted --track doi-only`. Mathlib: `update --upstream-target mathlib --automation T`, `record mathlib-pr-opened` and `mathlib-pr-merged`, then `update --status upstreamed` |

Three consequences for the tree:

1. **The selector is `--kind`, not `--track`.** `--track` already exists on
   `record` and `update` with another meaning (the DOI track, `palomar` or
   `doi-only`). `new --kind paper|library` writes the same `kind` key that
   `coverage.yaml` carries, so one word names the product everywhere.
   Renaming the DOI `--track` (to `--doi-track`, old spelling an alias)
   would remove the remaining ambiguity; it is listed under the smaller
   decisions.
2. **`lean-pkg help paper` and `lean-pkg help library`** become help
   topics, each printing its column above with the exact commands, beside
   the existing `environment`, `exit-codes` and `formatting` topics. The
   first page of `--help` names both in one line each.
3. **The Mathlib route records evidence; it does not prepare the PR.**
   lean-pkg has no verb that checks a Mathlib contribution against
   Mathlib's conventions (naming, docstrings, no `sorry`, the AI-disclosure
   note). That is a gap for track L, not a tree question: a future
   `mathlib check NAME` (read-only, like `reservoir check`) would sit in
   tier 2 beside `palomar check`, and does not change any name proposed
   here.

### Extensions

Per the 1.0 criterion "unknown commands dispatch to extensions": an unknown
`lean-pkg foo` runs `lean-pkg-foo` from `PATH` with the remaining arguments,
as git does, after the built-in names and aliases. This makes
`lean-pkg extract plan` work for the existing `lean-pkg-extract`
executable at no cost. `lean-exercise` serves a different audience
(teaching) and stays its own executable; a `lean-pkg-exercise` link would
make `lean-pkg exercise` work too. Extensions never shadow a built-in name.

The lab-specific workflow (the lab registry, committed mode, cluster
routes) is a candidate for an extension, but the lease and committed-mode
code sits inside the registry write path. Moving it out is a wave 3
question for the lab-coupling audit; for 1.0 the `lease` and `registry`
nouns are enough to take it off the newcomer's page.

### JSON output

The criterion asks for `--fields` and `--jq` on JSON output. Today
`--fields` exists on `status`, `list` and `board`. Proposal: `--fields`
on every command with `--json`, with the same dotted paths and unknown-field
error (exit 2) `status --fields` has; `--jq EXPR` runs `jq` when it is
installed and refuses (exit 2, naming `--fields`) when it is not, so lean-pkg
gains no dependency. The goldens in `tests/golden/json-keys.json` stay the
contract for the full key sets.

### Flag hygiene for 1.0

Changes that keep every old flag working:

- `--repo` means a checkout directory everywhere. The URL flag on
  `register`, `update` and `index add` becomes `--url`, with `--repo` kept
  there as a permanent alias; `report --repo` becomes `--target-repo`
  (alias kept). `--repo-dir` and `--checkout` become aliases of `--repo`.
- One confirmation idiom by effect: a command that changes the registry
  writes by default and takes `--dry-run`; a command that edits files in the
  checkout previews by default and takes `--write`; a command with an
  irreversible outside effect (a public flip, a filed issue) previews by
  default and takes `--yes`. `audit --fix` becomes `registry audit --write`
  (alias kept). `--force` keeps its per-command meaning but every help line
  names what it overrides.
- `--agent`: one rule, stated once in `help environment`: required for a
  write on a leased package, ignored otherwise, with a new
  `LEAN_PKG_AGENT` environment default.

### Generated command reference

After the refactor, full command documentation is generated from the
argparse tree into `docs/commands/` on the Pages site (a separate stream
builds the generator). The tree proposed here constrains it as follows:

1. **One page per canonical parser node**, named by its path:
   `docs/commands/lease-claim.md`, `docs/commands/comparator-config.md`.
   Pages are keyed by the 1.0 canonical name, never by an alias, so
   `claim`, `lease`, `renew`, `release`, `leases`, `init`, `migrate`,
   `validate`, `audit`, `board`, `wiki` and `promote` get no page of their
   own. Each alias is listed on its canonical page ("Also spelled") and in
   one generated `docs/commands/aliases.md`, from the same alias table the
   ARGV_TABLE rows test.
2. **The three pseudo-subcommands must become real subparsers first**
   (`comparator config`, `comparator host-check`, `formalization anchor`),
   with `comparator coverage` and `comparator migrate-signoff` split out of
   `comparator config`. A generator run before that either misses them or
   needs special cases that would have to be removed later. Until they are
   split, the generator should fail loudly on a node whose help names a
   positional keyword, rather than render a page that hides them.
3. **Split modes get their own pages:** `repo export`, `repo adopt` and
   `repo move` (today `release --fresh-repo`, `release --adopt-repo`,
   `update --path`); `comparator attach` and `comparator check` (today
   `comparator NAME --receipt` and `--check`); `publish` with `--yes`
   (today `promote --yes`). The old flags appear on the old command's page
   only as "moved to".
4. **Flag renames:** the generator prints the canonical flag first and its
   aliases after it: `--url` (alias `--repo` on `register`, `update`,
   `index add`), `--repo` (aliases `--repo-dir`, `--checkout`),
   `--target-repo` (alias `report --repo`), `registry audit --write` (alias
   `--fix`), and `--doi-track` if that rename is accepted.
5. **Groups and tiers come from the parser**, not from a list kept in the
   generator: each canonical node carries its tier (newcomer, author,
   coordination) and track (`paper`, `library` or both), so `--help`, the
   two track topics and the index page of `docs/commands/` are rendered from
   the same data and cannot drift.
6. **Executables and extensions.** `receipt comparator` is the canonical
   page for the comparator run; the `comparator-receipt` executable is an
   alias there. `lean-exercise` and `lean-pkg-extract` are documented on
   their existing pages, not generated with the tree; extensions found on
   `PATH` are never documented by the generator.
7. **Global flags** (`--registry`, `--events`, `--json`, `--commit`,
   `--no-commit`, `--push`, `--registry-snapshot`) go on one generated page
   and are linked, not repeated, from each command page; receipt
   `--commit SHA` (the receipt's commit) needs a distinct name before then
   (`--receipt-commit`, alias kept), or every receipt page shows two
   `--commit` lines.
8. `docs/cli.md` becomes the generated index; its hand-written 19,000-word
   tables are the input that the per-command help text must absorb before
   it is retired.

## 5. Migration and deprecation policy

RELEASING.md asks for two things that pull in different directions: "old
spellings are permanent aliases" and "an old spelling or flag keeps working,
with a warning, for at least one minor release before it is removed". This
proposal separates them.

**Aliases (renames).** A renamed command or flag is an alias forever. It
prints no warning in `--json` mode and never changes exit codes or output.
In text mode it prints one stderr line,
`note: 'lean-pkg claim' is now 'lean-pkg lease claim' (the old spelling keeps working)`,
which
`LEAN_PKG_NO_ALIAS_NOTE=1` silences. Each alias is an ARGV_TABLE row and
has its own help golden, so removing one fails the suite.

**Deprecations (removals of behavior).** A flag, mode, key or command
whose behavior goes away:

1. is announced in a `### Deprecated` CHANGELOG section with its
   replacement;
2. keeps working with a stderr `WARN: deprecated: ...` line naming the
   replacement and the earliest version that may remove it, and a
   `deprecations[]` key in `--json` output;
3. lives for at least **two minor releases and 60 days**, whichever is
   longer. "One minor release" is too short at the current cadence (65
   releases in two weeks); after 1.0 a removal is a major release anyway;
4. is removed only in a release whose `### Removed` section names it.

The inline `judged_as` and `lean_pkg_scaffold` keys (moved to
`lean-pkg-signoff.json`, warned today) are the precedent and would be the
first entries of the `### Deprecated` list.

**Formats.** A format changes only with a version bump and a migration
command that is a dry run by default. Readers accept every earlier version
forever when the file is evidence (receipts are never rewritten: rewriting
would break the bytes they bind); for state files (registry, claims,
index entries) the migration rewrites them and readers accept older versions
until the next major.

**Order of work.** (1) Accept the tree (a decision record). (2) Add the new
spellings as parsers that call the existing functions, with ARGV_TABLE
rows and goldens; old spellings stay canonical in the docs for one minor.
(3) Switch the docs and `llms` to the new spellings and add the alias notes.
(4) Tag 1.0 once the remaining criteria hold.

|---|---|---|---|---|---|

### What is missing for "versioned formats with migrations"

1. **Lower-tier receipt schema.** Add `schema: lower-receipt/1` to new
   receipts (additive: `gate` ignores unknown keys today). `gate` keeps
   accepting receipts without the key forever, read as version 0, because
   receipts are evidence bound to bytes and are never rewritten.
2. **Event log version.** Add an optional `v: 1` key to new events, and a
   documented list of event names with their keys (from the code, checked by
   a test). Readers treat a line without `v` as version 0.
3. **A formats page** (`docs/formats.md`): each format, owner (lean-pkg or
   an outside project), current version, accepted versions, migration
   command, and the rule for additive changes within a version (a new
   optional key keeps the version; a new required key, a removed key or a
   changed meaning bumps it).
4. **A compatibility corpus** in the tests: one fixture per accepted
   version of each lean-pkg-owned format, each read by the current code, so
   dropping support for an old version fails the suite.
5. **One discovery point for migrations.** Today migrations are spread over
   `migrate`, `claims migrate`, `index migrate` and
   `comparator config --migrate-signoff`. Rather than one command that
   rewrites everything, `doctor` would list every file that is not at the
   current version, with the exact migration command for each (read-only).
6. **Outside formats.** Record which Palomar and formalization.yaml
   versions a lean-pkg release targets, and the policy when they change.

## 8. Decisions for the maintainer

1. **Adopt the tiered tree with the package as the implied noun, and the
   two product tracks on the newcomer page?** Recommendation: yes. It meets
   the criterion with the least churn (no `lean-pkg package ...` prefix),
   puts five verbs in front of a newcomer, and shows the paper track and the
   Lean-package track as two columns of the same five verbs, selected by
   `new --kind paper|library`.
2. **Aliases: permanent, or deprecated and removed?** Recommendation:
   permanent, with a silenceable one-line note in text mode; warnings and
   removal only for behavior, never for spellings. Amend RELEASING.md
   to say so.
3. **Split `release` and fold `promote` into `publish --yes`?**
   Recommendation: yes. `release` is the most misleading name in the tree
   for an outsider, and `publish` is the name a newcomer will look for.
4. **Add `verify` as a wrapper of receipt, comparator receipt and gate?**
   Recommendation: yes, as a pure orchestrator that writes nothing the three
   steps would not, so the trust model is unchanged; it depends on wave 3
   for hosts without systemd.
5. **What does `lean-pkg` with no argument do?** Today it opens the board.
   Recommendation: short help (the five verbs) when no registry exists or
   stdout is not a tty, the board otherwise, which keeps the lab's habit.

Further, smaller: the deprecation window (two minors and 60 days is
proposed), `--repo` unification, renaming the DOI `--track` to
`--doi-track` and receipt `--commit` to `--receipt-commit` (aliases kept),
whether track L gets a read-only `mathlib check`, whether the event log gets
a version key or a documented "unversioned, append-only" status, and the
order against the command-reference generator (split the pseudo-subcommands
before generating, section 4).
