# Upgrading to 0.20.0 (from 0.19.0)

The changes merged after 0.19.0 that a package author should know about.
The machine-readable record is [0.20.0.yaml](0.20.0.yaml). This page is
filled in as pull requests merge, until 0.20.0 is cut. `lean-pkg doctor
--upgrade-from 0.19.0` prints the mechanical part, and the
[design](../design/upgrade-preflight.md) explains how the record is used.
The name 0.20.0 is provisional: the release is named by what it holds
(RELEASING.md, "When to tag"), and the record is renamed with it.

## Act before you check a page with internal claims

| Entry | PR | What changed | What to do |
|---|---|---|---|
| `ledger-judged-internal-claims` | #292 | An internal claim the comparator judged now counts as verified. `claims ledger` (promote stage) gave every claim with `claims.yaml` status `internal` the status `out-of-scope`, even when a passing comparator receipt had compared its statement. Now an internal theorem or lemma is judged (new JSON field `judged_internal: true`) when the comparator tier is clean for the package (a valid, passing comparator receipt bound to the gate-bound commit) and a configuration at that commit names its declaration by the rule that credits a reusable claim (a scaffold `TODO` name does not count). A judged internal claim gets the reusable claim's diagnostics and is `verified`, `open`, `blocked` or `unknown` on the same evidence; it is never required, so the package status and the required count are unchanged. Every other internal claim stays `out-of-scope`. `counts` and `ledger_digest` change for a package with a judged internal claim. The page adds an **Internal.** line to a result block that names an internal claim, and `coverage.md` adds `(internal)` to that claim's ledger status ([Claims ledger](../lifecycle.md#claims-ledger), [page](../page.md)). | Nothing for most package authors. A package whose `coverage.yaml` names an internal claim, or that has an internal claim a comparator configuration names, gets a different page: `lean-pkg page NAME --check` reports the README block (and `--site` files) stale until you run `lean-pkg page NAME --write` (and `--site DIR`) and commit. A script that read `out-of-scope` as "every internal claim" reads `judged_internal`. |

## Nothing required

| Entry | PR | What changed | What to do |
|---|---|---|---|
| `registry-dir-resolves-file` | #286 | `--registry DIR` and `LEAN_PKG_REGISTRY=DIR` now mean `DIR/lean-packages.yaml`, as the user-level default `~/.lean-pkg/registry` already did. An explicit directory was refused as `registry not found ... (resolved from flag)` even when it held the file; the lock and the event log now sit beside the resolved file. A directory without it is refused naming `DIR/lean-packages.yaml` ([registry resolution](../cli.md)). | Nothing for a package author. An explicit `--registry DIR` with no `--events` now writes the event log inside `DIR`, beside the registry file. |
| `signoff-smoke-configs` | #293 | `lean-pkg-signoff.json` (`lean-pkg-signoff/1`) accepts an optional `configs[<path>].smoke {reason}`: the configuration is a smoke check, a sanity theorem that tests the comparator set-up and states no result of the package. It is still judged, listed in the receipt and must pass, but its theorems credit no claim (claims ledger, `comparator config --coverage`, `receipt check`, `status`); `coverage check` (R11) asks no row for them and refuses the mark on a configuration that judges a row's claim; `page` names them on a "Smoke checks (not results)" line, never as results; `formalization` leaves them out of `status.main_results`, refuses a smoke headline and lets no smoke configuration cover a headline name; `index add` and `index check --clone` judge no index headline by a smoke theorem; `comparator config --from-claims` counts no smoke theorem as configured and refuses to scaffold into a smoke configuration; `claims mark --from-comparator --status reusable` refuses a smoke configuration. Read at the comparator receipt's commit and at `HEAD`. No schema bump; recorded receipts stay valid. lean-pkg 0.19.0 and older refuse a sidecar that uses the key ([smoke checks](../comparator.md#smoke-checks)). | Nothing for a package without one. To declare a sanity configuration, add `"smoke": {"reason": "..."}` to its entry in `lean-pkg-signoff.json`; every reader then needs this lean-pkg or newer. Rerun `coverage check` and `page --write`; no new receipt is needed. |
| `receipt-slurm-seal-sacct` | #294 | New flag `receipt slurm --seal-sacct [--user NAME]` (a field report). `receipt slurm` read `--sacct-file` (or live `sacct`) only for its own `COMPLETED` `0:0` check and the README elapsed/TotalCPU line; the written receipt sealed nothing, so on a host without Slurm the terminal state rested on a file any shell can write. With the flag the job's accounting record is sealed exactly as `receipt comparator --seal-sacct` seals a comparator receipt: `Start`..`End` (with a zone) must contain the verify log's `generated-at:` line and the account must be this one (live `sacct`) or `--user`; the normalized record `<c12>-slurm-<J>-sacct.txt` is written beside the receipt and the additive `slurm_sacct` block (schema `slurm-sacct-seal/1`) binds it. `gate`, `gate --check`, `receipt check` and every other validator of a lower-tier receipt then refuse a receipt whose sealed record is missing, uncommitted, re-hashed or edited ([Sealing the sacct record](../receipts.md#sealing-the-sacct-record---seal-sacct)). A receipt without the block is judged as before; the JSON only gains keys. | Nothing for a package author. To keep the job's accounting record with a lower-tier receipt, add `--seal-sacct` to `receipt slurm` (on a host without Slurm: `--sacct-file F --user NAME`, the record saved as documented) and commit the `-sacct.txt` record with the receipt. |
| `page-repo-head-anchors` | #291 | `page --repo DIR` read `coverage.yaml` and `claims.yaml` at DIR's committed HEAD but linked every Lean file and read every Lean statement at the commit the recorded gate receipt binds, and showed that receipt's facts, also on a candidate commit the receipt does not bind (a field report: a result added since the last gate linked to a commit where its file did not exist). The links and Lean statements now come from DIR's committed HEAD whenever the gate receipt does not bind it (HEAD or an evidence-only descendant of its commit, as `gate` and `formalization render --repo` decide); the page then shows no receipt fact, verifies no row, and a *Preview of commit* note names both commits. When the receipt validates at HEAD the page is unchanged. A receipt that binds HEAD but does not validate (axioms, `sorry` count, toolchain or Mathlib mismatch) is a failed check, not a preview: the page says *The recorded build check does not validate*, with the reason. JSON `repo_override` gains `head`, `anchor_commit`, `source` and `receipt_facts` {receipt, commit, included, binds_head, reason}. `page` without `--repo` is unchanged. See [In CI](../page.md#in-ci). | Nothing for most package authors. A CI `page --check --repo` keeps passing between gate runs: on a commit the receipts do not bind, the preview's differences from the receipt-bound README block and `--site`/`--html` files are warnings naming both commits (JSON `preview: true`, `current: null`); real problems still fail. A receipt that binds the commit but does not validate fails the check: repair it or run the gate again. Add `--strict-preview` to fail on preview drift too. |
| `page-check-strict-preview` | #291 | New flag `page --check --repo DIR --strict-preview`. Without it, when DIR's committed HEAD is a preview (the recorded gate receipt does not bind it), the differences that come only from the preview (the README block, `--site` and `--html` files differing from the receipt-bound files) are warnings naming both commits, and the check exits 0; with it they are problems (exit 1). Real problems exit 1 either way: a missing README or page block, unbalanced markers, a missing lean-pkg credit, an unbacked site acknowledgment, a missing `--site`/`--html` file, a private-string hit, a receipt that binds HEAD but does not validate. Refused (exit 2) without both `--check` and `--repo`. `page --json` gains `preview`; under a preview `current` is `null`. See [In CI](../page.md#in-ci). | Nothing required. A CI job that should fail whenever the committed page differs from the candidate's preview adds `--strict-preview`. A script reading `current` from `page --check --repo --json` reads `preview` first. |
