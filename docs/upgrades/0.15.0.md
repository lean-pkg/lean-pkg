# Upgrading to 0.15.0 (from 0.14.0)

The changes merged after 0.14.0 that a package author should know about.
The machine-readable record is [0.15.0.yaml](0.15.0.yaml). This page is
filled in as pull requests merge, until 0.15.0 is cut. `lean-pkg doctor
--upgrade-from 0.14.0` prints the mechanical part, and the
[design](../design/upgrade-preflight.md) explains how the record is used.

Nothing so far is required of a package author, except to re-render a page
that shows a verified result the comparator did not check (#270). One
default changes: a new paper scaffold starts on the current LTS stack. Opting an existing package
into a stack is optional:

| Entry | PR | What changed | What to do |
|---|---|---|---|
| `lts-stack-opt-in` | #264 | Stage 1 of [proposal 0004](../proposals/0004-math-lts-stack.md). `lean-pkg new --stack NAME\|current\|none` pins `lean-toolchain` and the Mathlib require to a declared [LTS stack](../stacks/README.md) and writes `stack: NAME` into `coverage.yaml`. **New default:** `new --kind paper` takes the current stack (`lts-2026.10`: Lean `v4.35.0`, Mathlib `v4.35.0`, where 0.14.0 wrote `v4.35.0-rc2`); `--kind library` keeps the newest pins. `coverage.yaml` accepts the optional key `stack` (both kinds). `doctor NAME` (new optional argument) and `verify` check the committed `lean-toolchain`, the Mathlib commit of `lake-manifest.json` and the comparator receipt's tool digests against the stack, and warn on a difference, a stack past its window or one this lean-pkg does not declare; they never refuse. Both gain the `--json` key `stack`. The page says "Built on lean-pkg stack NAME" when the pins match. The scaffold's `lakefile.toml` names its library in `defaultTargets`, so a bare `lake build` builds it. lean-pkg 0.14.0 and older refuse the `stack` key. | Nothing for an existing package. To opt in, add `stack: lts-2026.10` to `coverage.yaml`, require this release or later, and move the pins as [lts-2026.10](../stacks/lts-2026.10.md) says; `lean-pkg doctor NAME` then says whether they match. For the previous scaffold pins, `new --stack none`. An existing scaffold can add `defaultTargets = ["MOD"]` after the `name` line of its `lakefile.toml`. |
| `index-built-on-credits` | #267 | [Proposal 0007](../proposals/0007-index-built-on-credits.md) (draft). An `index-entry/2` accepts the optional key `built_on`: credits for the third-party Lean code the package depends on or adapts (`name`, https `url`, `authors`; optional `license`, 40-hex `pin`, `relation` `depends-on` or `adapted-from`, `note`), validated strictly and never evidence. `index render` adds a *Built on* column and section to `index/README.md`. `index add` gains `--built-on-file FILE` and `--replace` (re-pin an existing entry, carrying its `built_on` over); `index add --json` gains `replaced` and `built_on`. `index check` validates the key and, with `--clone` or `--repo-dir`, warns when a `depends-on` pin differs from `lake-manifest.json` at the pin. lean-pkg 0.14.0 and older refuse the key. | Nothing for a package author. Re-pin an index entry with `index add --replace`, which keeps its credits; credit a library with `--built-on-file` ([format](../index-catalog.md#credits-built_on)). |
| `index-check-uncredited-dependencies` | #269 | [Proposal 0007](../proposals/0007-index-built-on-credits.md) accepted (2026-10-18, after #267 had merged as its implementation). `index check --clone` (or `--repo-dir`) warns on each `lake-manifest.json` package at the entry's pin that is not Mathlib, one of Mathlib's own dependencies or Lean core and that no `built_on` credit names (by URL, with or without `.git`, or by name). Exit status and `ok` are unchanged; `--json` gains the per-entry key `uncredited_dependencies` (`name`, `url`). [The rule](../index-catalog.md#credits-built_on) for Mathlib's dependencies: a listed name or URL, or an `inherited` package from the leanprover-community or leanprover organizations. | Nothing for a package author. An index entry that requires a non-Mathlib Lake library credits it (`index add --replace --built-on-file`). |
| `page-uncompared-verified-rows` | #270 | A verified row of the page said "every check of this result passed (the build, and the statement comparison)" even when its claims were never compared: the comparator is required only for `reusable` claims, so the ledger calls an experimental or internal claim verified on the build alone. A row now says "(the build, and the statement comparison)" only when a passing comparator configuration at the gate-bound commit judged every claim it names; otherwise "every check that applies to this result passed (the build; its statement was not compared by a second checker)". When not every verified result was compared, the summary line adds "(for K of them a second checker also compared the statement)". Same text in `--site` and `--html`; the word *verified* and the `--json` keys are unchanged. | A package whose page has a verified result that no passing comparator configuration checked: rerun `lean-pkg page NAME --write` once (`page --check` reports the block stale until then). Of the published packages only rmt-foundations has a page block, and all its rows are compared, so it does not change. |
