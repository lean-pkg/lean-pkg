# Upgrading to 0.24.0 (from 0.23.0)

The changes merged after 0.23.0 that a package author should know about.
The machine-readable record is [0.24.0.yaml](0.24.0.yaml). This page is
filled in as pull requests merge, until 0.24.0 is cut. `lean-pkg doctor
--upgrade-from 0.23.0` prints the mechanical part, and the
[design](../design/upgrade-preflight.md) explains how the record is used.
The name 0.24.0 is provisional: the release is named by what it holds
(RELEASING.md, "When to tag"), and the record is renamed with it.

Nothing so far is required of a package author.

## Nothing required

| Entry | PR | What changed | What to do |
|---|---|---|---|
| `palomar-check-module-root-shadowed` | #405 | `palomar check` reports a comparator configuration whose `challenge_module` or `solution_module` has a top-level root `R` that is also a top-level `R.lean` or `R/` of a dependency: the `error` gap `challenge.module_root_shadowed` or `solution.module_root_shadowed`, the code Palomar's full preflight refuses with. Still offline: each dependency `lake-manifest.json` pins is read from its checkout under `.lake/packages/<name>/` only at the pinned revision (a path dependency inside the repository from the commit), at its root and each literal `srcDir`. A dependency not read is named in `not_checked`, and a bare `Challenge`, `Solution` or `Main` root is then the `warn` gap `challenge.module_root_generic` or `solution.module_root_generic` ([#404](https://github.com/lean-pkg/lean-pkg/issues/404), [palomar check](../commands/palomar-check.md), [why a bare Challenge collides](../faq.md#palomar-readiness)). | For the error, move the module under a package-qualified root such as `MOD.Challenge` (the layout `lean-pkg new` scaffolds), rebuild, commit, re-run `comparator-receipt` and re-gate. The warning changes nothing: run `lake build` and re-run `palomar check` to settle it. |
