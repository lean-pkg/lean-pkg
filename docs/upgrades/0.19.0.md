# Upgrading to 0.19.0 (from 0.18.1)

The changes merged after 0.18.1 that a package author should know about.
The machine-readable record is [0.19.0.yaml](0.19.0.yaml). This page is
filled in as pull requests merge, until 0.19.0 is cut. `lean-pkg doctor
--upgrade-from 0.18.1` prints the mechanical part, and the
[design](../design/upgrade-preflight.md) explains how the record is used.
The name 0.19.0 is provisional: the release is named by what it holds
(RELEASING.md, "When to tag"), and the record is renamed with it.

Nothing so far is required of a package author:

| Entry | PR | What changed | What to do |
|---|---|---|---|
| `json-stdout-only` | #281 | Under `--json`, stdout is the JSON document alone (a field report from a two-library release campaign). `comparator-receipt --estimate --json` (also `lean-pkg receipt comparator --estimate --json`) printed the stage lines, the per-slot progress and the streamed judge output on stdout before the JSON, so `json.loads(stdout)` failed although every slot passed; that output now goes to stderr. The global `lean-pkg --json` before `receipt comparator` was ignored: it now means the runner's own `--json` for `--estimate`, `--verify-oleans`, `--attempts` and `--seal-sacct`, and a run or `--prepare` under it is refused (exit 2, one JSON error). `receipt slurm --template --json` printed the raw script; it now prints `{ok, template}`. See [Estimate first](../comparator.md#stages-and-prepare). | Nothing for most package authors. A script that cut the estimate JSON out of mixed stdout can parse stdout whole; `comparator-stages/04-comparator.estimate.json` is unchanged and remains the recommended machine-readable source. Drop a global `--json` in front of a `receipt comparator` run or `--prepare`. |
| `public-safety-long-line-stream` | #282 | A field report had `public-safety` (history, strict, whole repository, `--gzip-limit 512M`) killed for memory at a 2 GiB limit, on a gzip file holding one 333,681,168-byte JSON line with four-byte UTF-8 characters, inside the decode limit and the ratio guard. The gzip path kept the whole unfinished line, decoded it in one piece and split it into lines again; UTF-16/32 gzip content was held and decoded whole. Decoded text now goes through an incremental decoder (a multi-byte character split between two reads is never cut) and a line scanner that scans a long line in the same overlapping chunks as it arrives, with the same line numbers and the same one hit per pattern per line. On a 64 MiB line the peak traced memory went from about 540 MiB to about 8 MiB. Limits, guards, strictness, which files are scanned and the hits reported are unchanged. | Nothing for a package author. A scan that ran out of memory on a long line in a gzip file can be run again. |

The same pull request adds [Seeding the Mathlib archive
cache](../comparator.md#seeding-the-mathlib-archive-cache) to the comparator
page: how a `--prepare` whose `cache-get` downloads keep failing can be fed
from a verified real copy of Mathlib's public cache archives, never from
proof objects or build outputs.
