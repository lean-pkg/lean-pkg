# Upgrading to 0.21.0 (from 0.20.0)

The changes merged after 0.20.0 that a package author should know about.
The machine-readable record is [0.21.0.yaml](0.21.0.yaml). This page is
filled in as pull requests merge, until 0.21.0 is cut. `lean-pkg doctor
--upgrade-from 0.20.0` prints the mechanical part, and the
[design](../design/upgrade-preflight.md) explains how the record is used.
The name 0.21.0 is provisional: the release is named by what it holds
(RELEASING.md, "When to tag"), and the record is renamed with it.

Nothing so far is required of a package author.

## Nothing required

| Entry | PR | What changed | What to do |
|---|---|---|---|
| `claim-axioms-narrower-print` | #299 | The per-claim axiom check no longer refuses a claim whose `#print axioms` output names fewer axioms than the environment walk (under the Lean module system `#print axioms` on a structure type can print none); the walk is the verdict and the narrower print is a check line. A `#print axioms` output naming an axiom the walk did not find is still refused. | Nothing; a package refused for this reruns `receipt slurm` on the same saved files. |
| `producer-bytecode-fingerprint` | #297 | The receipt key `producer` gains `bytecode_tag`, `bytecode_files`, `bytecode_sha256` and `other_bytecode_files`: `sources_sha256` covers the sources only, and Python executes a module from its cached `__pycache__/<name>.<cache_tag>.pyc`, so the running interpreter's own caches are now fingerprinted at the run start (null without a cache tag) and every other `.pyc`/`.pyo` is counted. Never compared during a run. | Nothing. A pin or audit that cites `sources_sha256` as the code that ran should also read `bytecode_sha256`. |
| `receipt-producer-slurm-comparator` | #300 | `receipt slurm` and `receipt comparator` now write the additive key `producer`, the lean-pkg that wrote the receipt, with the shape `receipt systemd --run` seals, built when the receipt is written (a field report: an evidence chain mixing lean-pkg versions was invisible). For `receipt slurm` that is the collector, not the lean-pkg inside the job, and it is always recorded; `receipt slurm --json` gains `producer`. No path, host or user name ([receipts](../receipts.md#which-lean-pkg-wrote-a-receipt-producer-skew)). | Nothing. `gate`, `gate --check`, `receipt check` and the comparator validator ignore the key; older receipts keep validating, and an older lean-pkg reads the new ones unchanged. |
| `producer-skew-status-doctor` | #300 | New flag `doctor --package NAME`, and a `producer` block in `status NAME`: for the package's gate receipts, the lean-pkg that wrote each against the running one. A WARN names the breaking record entries that touch receipts, gate or claims between an older producer and the running lean-pkg, with `lean-pkg doctor --upgrade-from vPRODUCER --source DIR`, and always flags a producer newer than the running lean-pkg; otherwise info only. Never a refusal or an exit 1. `status --json` gains `producer_skew`, `doctor --json` with `--package`. The breaking entries ship as `src/lean_pkg/data/upgrade-breaking.yaml`, generated from the records ([receipts](../receipts.md#which-lean-pkg-wrote-a-receipt-producer-skew)). | Nothing required. After moving to another lean-pkg, run `lean-pkg status NAME`; on a WARN, read the named entries, and upgrade lean-pkg before trusting `gate` on a receipt a newer one wrote. |

PR #296 (release tooling: an upgrade record has one entry per pull request
unless each of that pull request's entries is marked `split: true`, which the
multi-entry pull requests of 0.11.0, 0.12.0 and 0.20.0 now are; it replaces
the narrower rule of #290) was read for this record; it changes nothing for a
package author.

PR #298 (tests only: two test helpers named `setup` are renamed so pytest 7
and 8 no longer take them for nose-style module setup, and the committed-mode
tests ignore the host's global git config, whose `core.hooksPath` hid their
fake remotes' hooks) was read for this record; it changes nothing for a
package author.

PR #301 (documentation and messages: every runnable command has an example
in the command reference, and `index check` and `search --record` name their
local-clone flag `--repo` in their messages, help and `lean-pkg llms`, as
`--help` already did; `--repo-dir` still works) was read for this record; it
changes nothing for a package author.

PR #302 (messages and docs: `register` and `update` name their URL flag
`--url` in their messages, the agent contract and every `register` example,
as `--help` already did; `--repo` still works, and an empty one is now
reported as `--url must not be empty`) was read for this record; it changes
nothing for a package author.

PR #303 (scripts/bootstrap-collaborator.sh registers the package with
`register --url`, and with `--repo`, its old spelling, when the installed
lean-pkg is older than 0.11.0 or its version cannot be read) was read for
this record; it changes nothing for a package author.

PR #304 (scripts/bootstrap-collaborator.sh: its checks are written as
`if ...; then ...; else ...; fi` instead of `A && B || C`, so ShellCheck
reports nothing) was read for this record; it changes nothing for a package
author.

PR #305 (ShellCheck disable comments for two intended findings: SC2016
file-wide in `verify-comparator.sh`, recorded as its vendored local change
(5), and SC2086 in the test stub `tests/fixtures/lake-stub.sh`) was read for
this record; it changes nothing for a package author.

PR #306 (`make shellcheck`, part of `make check`, lints lean-pkg's own shell
scripts with ShellCheck, and CI runs it with a pinned ShellCheck; the
vendored `comparator-check.sh` is not linted) was read for this record; it
changes nothing for a package author.
