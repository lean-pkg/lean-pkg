# Upgrading to 0.23.0 (from 0.22.0)

The changes merged after 0.22.0 that a package author should know about.
The machine-readable record is [0.23.0.yaml](0.23.0.yaml). This page is
filled in as pull requests merge, until 0.23.0 is cut. `lean-pkg doctor
--upgrade-from 0.22.0` prints the mechanical part, and the
[design](../design/upgrade-preflight.md) explains how the record is used.
The name 0.23.0 is provisional: the release is named by what it holds
(RELEASING.md, "When to tag"), and the record is renamed with it.

Nothing so far is required of a package author.

## Nothing required

| Entry | PR | What changed | What to do |
|---|---|---|---|
| `gate-check-palomar-advisory-intent` | #391 | `gate --check` prints its Palomar advisory (`WARN: palomar: not submittable ...`) only for a package that aims at Palomar: `upstream_target: palomar` or a recorded Palomar entry, and a status other than scratch, archived or upstreamed, the predicate `registry audit` uses ([#387](https://github.com/lean-pkg/lean-pkg/issues/387)). Any other package gets no WARN. JSON `palomar_check` gains `skipped`: null for a package aiming at Palomar, `"not aiming at Palomar"` for any other, whose readiness fields are still filled. `publish --dry-run` and `palomar check` are unchanged ([gate](../commands/gate.md)). | Nothing. To keep the advisory for a package headed to Palomar, run `lean-pkg update NAME --upstream-target palomar`; a script reading `gate --check --json` `palomar_check` sees one more key. |
| `report-intake-fields` | #389 | New `report` flags `--expected TEXT` (fills What you expected), `--workaround TEXT` (a Workaround section after it) and `--blocking yes\|no` (a Blocking line before Version), each rendered only when given and redacted like `--body`. Every report body starts with the marker `<!-- lean-pkg-report/1 -->`, and `--json` gains `schema` ([report](../commands/report.md)). | Nothing. A script that reads the body by line number sees one more line at the top. |
| `gate-check-next-command` | #390 | `gate NAME --check --agent A` runs the check with one stderr note (`--check` takes no lease; `--agent A` is for the writing gate) instead of a usage error, exit 2; `--check --refresh-formalization` is still refused. A passing check, on a status the writing gate takes, ends with `next: lean-pkg gate NAME --receipt R ... --agent A`, the evidence flags it was given and `--agent A` (else the placeholder `AGENT`); `--json` gains `next_command` (`null` when the check fails or the status needs another step first). After `--check --repo DIR` away from the registered `local_path` a line adds that the writing gate binds the registered checkout ([#386](https://github.com/lean-pkg/lean-pkg/issues/386), [gate](../commands/gate.md)). | Nothing. Run the printed `next:` command to record the gate, in the registered checkout. |
| `registry-recommended-version` | #395 | New [`registry recommend X.Y.Z`](../commands/registry-recommend.md) sets the registry's optional top-level `lean_pkg: {recommended: X.Y.Z}` (additive; the schema stays version 3, and an older lean-pkg ignores the key and keeps it) with the log-only event `registry-recommended` ([#388](https://github.com/lean-pkg/lean-pkg/issues/388)). On a lean-pkg older than that (compared on `X.Y.Z`), every writing command ends with one stderr line `lean-pkg: notice: this is lean-pkg A.B.C; the registry recommends X.Y.Z (upgrade: ...)`, offline and never a refusal; a registry write's `--json` gains `lean_pkg_skew` {`running`, `recommended`} (absent when not older). `doctor` gains a `recommended` line, and `registry validate` checks the key's shape. | Nothing required. Whoever upgrades a shared registry can run `lean-pkg registry recommend X.Y.Z --commit`. |

PR #384 (documentation: proposals 0002, 0003, 0008 and 0009 marked
implemented in 0.22.0; no code changes) was read for this record; it changes
nothing for a package author.
