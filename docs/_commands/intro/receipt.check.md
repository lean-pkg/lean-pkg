| Form | What it does | Key flags |
|---|---|---|
| `receipt check` | an outside referee's check of a published package: reads no registry, opens no network connection and never runs Lean. Clones `--repo` privately (local transport only; its working tree is never read or changed), checks out the published ref (`--at`, default HEAD) and runs `gate`'s and `comparator`'s own validators on the receipts under `.lean-receipts/` that bind `--commit` (a JSON file named for the commit that is not a receipt fails, unless its `schema` is one of the comparator runner's own records, such as `comparator-stages/1`, which is skipped and listed): the binding (evidence-only descendants, with `gate`'s exemption for a `formalization.yaml` at the package root that differs only in derived keys, printed when applied; docs-only ones too when `lean-pkg-binding.yaml` committed at the commit opts in, by default, reported first as an `opt-in` check (`PASS`, or `SKIP` with the reason for a file that says `false`, does not validate, was added after the commit, or is ignored by `--evidence-only`); for a package without that file, with `--docs-descendants`, the referee's choice, printed with the result, which a committed `false` or invalid file overrides; never with `--evidence-only`; the `rule:` line says which rule bound and who chose it, `--json` `docs_descendants`, `evidence_only` and `opt_in {source, commit, path, build_inputs, file, problems}`), the toolchain and Mathlib pins at the commit, every SHA-256 (configurations, logs, the redacted verify log, `manifest_sha256` and the other additive evidence keys, the olean manifest record), the claims at the commit, the comparator configurations naming every reusable theorem claim, `coverage.yaml` (R11) and the README page block against the receipts. One line per check, `PASS`, `FAIL` or `SKIP` (not applicable, with the reason); `--json` lists them all. A toolchain on lean-pkg's toolchain advisories list adds one `WARN: toolchain advisory ...` line per entry after the verdict, never a failure (JSON `toolchain_advisories[]`; [toolchain advisories](../receipts.md#checking-a-published-packages-receipts-receipt-check)). `--corroborate` is the one networked check: each receipt with a `ci` block (a GitHub Actions run) is corroborated against the public GitHub REST API (level 2: the attempt it names completed with success on the commit, in the package's repository by numeric id, a job on a GitHub-hosted runner, exactly one `lean-pkg-receipt` annotation binding the committed receipt and log bytes, the workflow calling lean-pkg's pinned `verify.yml` at a 40-hex commit whose content is in the shipped pin list), one `ci level 2 CHECK` row per check, failing when it does not reach level 2; a 404, 403 or 429 (naming `GH_TOKEN`), a network error and a redirect off api.github.com fail closed. `--github OWNER/REPO` names the package's repository (default: the receipt's `ci.repository`, printed); `GH_TOKEN` or `GITHUB_TOKEN` only raises the rate limit and is never printed or written; `--json` gains `ci {level, rows[]}`, `github` and `network: true` ([level 2](../receipts.md#corroborating-the-run-level-2---corroborate)). Exit 0 only when no check fails, 1 otherwise, 2 on a usage error (`--docs-descendants` with `--evidence-only` is one). Re-running Lean is the comparator step of docs/trust-model.md, "Re-verify a page yourself". The 1.0 command tree's read-only verb on the `receipt` noun; the spelling `verify-receipts` is reserved for its alias table | `--repo DIR` `--commit SHA` `--at REF` `--docs-descendants` `[--corroborate [--github OWNER/REPO]]` `--evidence-only` `--json` |
