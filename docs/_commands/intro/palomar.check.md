A Challenge's imports beyond Mathlib's vocabulary (Init, Std, Lean, Mathlib, Batteries and the other libraries Mathlib brings in) are `warn` gaps, never errors ([#369](https://github.com/lean-pkg/lean-pkg/issues/369)): `challenge.statements_module` for the statements module `claims.yaml` declares (`statements_module`; "trusted by declaration, read it", with lean-pkg's refusal appended when the module fails its check) and `challenge.import` for any other module. A Challenge that imports Mathlib only gets neither ([A statements module for conditional claims](../comparator.md#a-statements-module-for-conditional-claims)).

A comparator configuration whose `challenge_module` or `solution_module` has a top-level root `R` (the text before the first `.`) that is also a top-level `R.lean` or `R/` of a dependency's source tree is an `error` gap, `challenge.module_root_shadowed` or `solution.module_root_shadowed`, the code Palomar's full preflight uses ([#404](https://github.com/lean-pkg/lean-pkg/issues/404)): the resolver may take the dependency's file instead of the submitted one. The check stays offline: it reads each dependency `lake-manifest.json` pins at the commit from its checkout under `.lake/packages/<name>/` (a local build artifact) only when that checkout's HEAD is the pinned revision, and a path dependency inside the repository from the commit; it looks at the package root and each `srcDir` the dependency's lakefile states literally. A dependency it could not read (not checked out, another revision, not a git checkout) is named in `not_checked`, and then a bare root `Challenge`, `Solution` or `Main` is a `warn` gap, `challenge.module_root_generic` or `solution.module_root_generic`. The fix for both is a package-qualified module such as `MOD.Challenge`, the layout `lean-pkg new` scaffolds. When every dependency was read, `not_checked` no longer lists the shadowing check.
