| Form | What it does | Key flags |
|---|---|---|
| `palomar prepare NAME` | build a Palomar submission bundle; no network request, nothing submitted. Default directory `<checkout>/.lean-receipts/palomar-<HEAD12>/` (`--out DIR` elsewhere; an existing non-empty target is refused, never overwritten): `formalization.yaml` (the renderer's output, schema-valid; placeholders are warnings), `configs/<path>` (every comparator configuration tracked at HEAD, byte-identical, and the [headline configuration](../comparator.md#headline-configuration-the-papers-main-results) when one is declared; README.txt names it for the main-results entry and its `record` command; JSON `headline_config`), `receipts/<file>` (the recorded gate and comparator receipts, validated against HEAD: bound to it or to an evidence-only ancestor), `README.txt` (a staged handoff checklist, in order: 1 static readiness, what lean-pkg checked and that it is not Palomar's full preflight; 2 the full mechanical preflight, PalomarSubmission's reusable workflow `.github/workflows/submission.yml` with `mode: full` and `execution_profile: palomar-standard-v1`, `uses:` and `pipeline_commit` pinned to the same full commit the live contract names, where a local `lake build`, a repository CI job or a standalone comparator run (the comparator receipt included) is not equivalent, continuing only on `status: pass`; 3 the approval fields to show the user before intake, `repository`, `commit` and `comparator_config_path` pre-filled and `authorization_relationship` left for the user to state; 4 intake, proof and cleanup, linked to Palomar's live agent contract <https://submit.palomar-registry.org/llms.txt>, not copied; 5 editorial review; 6 registration only on the user's explicit decision; 7 the `record ... palomar-submitted` command. lean-pkg automates none of them), `MANIFEST.sha256` (`sha256  path` per file; `sha256sum -c MANIFEST.sha256`). Refused (exit 1, nothing written, `--dry-run` included) without either receipt or when one is not bound to HEAD, without consent, when the render fails the schema, when `palomar check` finds any `error` gap at HEAD (each listed as `✗  CODE: detail` with its fix; `warn` gaps never refuse and print as `lean-pkg: warning: palomar check: ...`), or on blocking `public-safety` hits in the bundle (scanned like a fresh-history export). Records `palomar-prepared` {commit, bundle, bundle_sha256 (sha256 of MANIFEST.sha256)}. `--dry-run` runs every check and prints the plan, writing nothing. `--json`: {ok, name, dry_run, bundle, commit, configs[], handoff {stages[], approval_fields {repository, commit, comparator_config_path, authorization_relationship (always null: the user states it)}, agent_contract, full_preflight {workflow, mode, execution_profile}}, files[], bundle_sha256, placeholders[], public_safety {block_hits, warn_hits}, palomar_check {ready, commit, errors, warns, codes[], command}, manuscript_findings, warnings[], event}; `manuscript_findings` is the claims ledger's summary of what the formalization found in the manuscript (one text line when there is one; not in the bundle, never a refusal) | `[--out DIR]` `[--dry-run]` |
